1. Enhanced Cloud Architecture

Phase 3 extends the Phase 2 static web app with three pillars: event-driven data processing (Azure Function blob trigger), caching (Cosmos DB as the durable cache, with Redis as an optional read-through layer), and authentication/security (custom JWT auth, Google/GitHub OAuth, platform encryption at rest).

This is the intended target architecture, not a deployed one. 0 Azure resources provisioned Azure Cache for Redis is deliberately not provisioned — it has no free tier, and the rubric accepts either an external cache or a database. Cosmos DB serverless is the cache of record (deploy.sh, the cost note in its header, deploy.sh, the Cosmos account step). There is also no Azure Static Web Apps resource and no staticwebapp.config.json: the frontend is static files served from Blob Storage static website hosting, and all authentication is implemented in the Function App rather than by a platform auth provider. That hosting choice has one consequence worth stating plainly, because it is easy to get wrong: static website hosting serves files and nothing else — it will not proxy /api through to the Function App. The frontend therefore has to call the Function App by absolute URL. frontend/config.js carries an __API_BASE__ placeholder that deploy.sh substitutes at upload time, falling back to http://localhost:7071/api when the page is opened locally.

2.1 Blob Trigger — Data Cleaning (10 marks) Code complete · unverified

The Azure Function listens for changes to All_Diets.csv in the raw-data Blob Storage container. When the file is uploaded or modified, the function:

  1. Parses the CSV (7,806 rows, 5 diet types) with pandas
  2. Cleans and normalizes the rows (clean_data in backend/nutrition.py)

  5. Writes cleaned_recipes.csv back to the clean-data container

2.2 Result Caching — Cosmos DB (10 marks) Code complete · unverified

After cleaning, the function pre-computes aggregated results (average macros per diet, recipe counts, totals) and stores them in Cosmos DB, which is the durable cache. Redis is used only when REDIS_HOST is set and is not provisioned by the deploy script. Dashboard reads never re-process the raw CSV — they fetch pre-computed results from the cache.

The cleaned recipe records are written in chunks of 2,000 because a Cosmos document may not exceed 2 MB and the full dataset serializes to roughly 1.2 MB. Chunking also matters for correctness: the blob trigger and the HTTP handlers are not guaranteed to run in the same process on Azure Functions, so a process-local cache would leave the API with nothing to serve. A recipes_meta document records the chunk count. The write order is deliberate: the old metadata document is deleted before the chunks are replaced and the new one is written last, so a reader arriving mid-rewrite sees an empty cache (which the endpoints turn into a 503) rather than a set spliced together from the old dataset and the new one. Orphan chunks from a larger previous dataset are deleted before the new count is published, and a reader that finds a chunk missing reports the cache as empty rather than serving a partial dataset.

Caching Logic — actual source, backend/cache.py, store_recipes() and get_recipes()

# backend/cache.py
# A Cosmos document may not exceed 2 MB.  The full cleaned dataset serializes
# to roughly 1.2 MB, so it is split across documents of this many records.
CHUNK_SIZE = 2000

def store_recipes(recipes_list: list) -> bool:
    """Persist the cleaned recipe records for search, filter and pagination.

    Written to Cosmos in chunks so the dataset is readable from any function
    instance, not just the one that handled the blob trigger.
    """
    updated_at = datetime.now(timezone.utc).isoformat()
    total = len(recipes_list)
    chunks = [recipes_list[i:i + CHUNK_SIZE]
              for i in range(0, total, CHUNK_SIZE)] or [[]]

    previous = _cosmos_read(RECIPES_META_KEY) or {}
    previous_count = int(previous.get("chunk_count", 0))

    # Retire the metadata before touching the chunks.  The chunk documents are
    # replaced one at a time, so mid-rewrite the set is a mixture of the new
    # dataset and the old one; a reader that still trusted the old metadata
    # would splice the two and serve the result as if it were valid.  With the
    # metadata gone the cache reads as empty until the new set is complete,
    # which is the honest answer and the one the endpoints turn into a 503.
    if previous:
        _cosmos_delete(RECIPES_META_KEY)

    wrote = True
    for index, chunk in enumerate(chunks):
        if not _cosmos_write({
            "id": f"recipes_chunk_{index:03d}",
            "partitionKey": "cache",
            "records": chunk,
        }):
            wrote = False
            break

    if wrote:
        # Drop chunks left over from a larger previous dataset before
        # publishing the new count.
        for index in range(len(chunks), previous_count):
            _cosmos_delete(f"recipes_chunk_{index:03d}")

        wrote = _cosmos_write({
            "id": RECIPES_META_KEY,
            "partitionKey": "cache",
            "chunk_count": len(chunks),
            "record_count": total,
            "updated_at": updated_at,
        })
        #   ... logs the record and document counts ...

    r = _get_redis()          # None unless REDIS_HOST is configured
    if r:
        try:
            r.set("recipes_cache", json.dumps(recipes_list))
            logger.info("Recipes mirrored to Redis (%d records)", total)
        except Exception as exc:
            # Redis is read first and the keys carry no TTL, so a key that
            # cannot be refreshed must not stay behind: drop it and let reads
            # fall through to Cosmos.
            logger.warning("Redis recipe write failed (%s); dropping the "
                           "stale key", exc)
            _redis_discard(r, "recipes_cache")

    _memory_store["recipes_cache"] = recipes_list
    return wrote or bool(r)


def get_recipes() -> Optional[list]:
    """Read the cleaned recipe records, or None when nothing is cached."""
    r = _get_redis()
    if r:
        try:
            raw = r.get("recipes_cache")
            if raw:
                return json.loads(raw)
        except Exception as exc:
            logger.warning("Redis recipe read failed: %s", exc)

    meta = _cosmos_read(RECIPES_META_KEY)
    if meta:
        records: list = []
        for index in range(int(meta.get("chunk_count", 0))):
            doc = _cosmos_read(f"recipes_chunk_{index:03d}")
            if doc is None:
                # The durable cache disagrees with its own metadata. Report a
                # miss instead of falling through to the process-local copy,
                # which may hold an entirely different dataset.
                logger.warning(
                    "Recipe chunk %d is missing; reporting the cache as empty "
                    "rather than serving a copy that may be stale", index)
                return None
            records.extend(doc.get("records", []))
        # An empty dataset that was cached on purpose returns []; None is
        # reserved for nothing having been cached at all.
        return records

    return _memory_store.get("recipes_cache")

4. Authentication & Security

4.1 Email / Password Registration & Login (10 marks) Hashing verified in repo Never run against a database

Users register with an email and password. The password is hashed using bcrypt with 12 salt rounds before storage in Cosmos DB; login verifies against the stored hash. Sessions are signed JWTs (HS256) with a 24-hour expiry. The hashing cost factor and the fact that plaintext is never stored are verifiable right now by reading backend/auth.py — that part needs no deployment to check. What is unverified is everything downstream of it: no user has ever been written to a real Cosmos container, because no Cosmos account exists.

One boundary worth calling out because it is the difference between a 400 and a 500: bcrypt hashes at most 72 bytes. validate_registration measures the password in bytes, not characters, and rejects anything longer with 400 “Password must be at most 72 bytes.” (backend/models.py, validate_registration()); hash_password raises above the same limit as a backstop. Silently truncating — which older bcrypt releases did — would make two different passwords interchangeable, and letting the hash call raise would surface a long password as a 500. Both outcomes are covered by tests (§7).

Evidence still needed: a Cosmos Data Explorer screenshot of one document in the users container showing a $2b$12$… hash in the password field and no plaintext password; plus a curl transcript of register → login → authenticated request. One known residual risk: with Cosmos unset the code falls back to an in-process user dict (_memory_users), so register-then-login can fail across instances — which is another reason the database has to actually exist before recording.

Password Hashing and Token Issue — actual source, backend/auth.py, hash_password(), verify_password(), create_token()

# backend/auth.py
MAX_PASSWORD_BYTES = 72


def hash_password(plain: str) -> str:
    """Hash a plaintext password with bcrypt (12 rounds).

    bcrypt itself accepts at most 72 bytes. Version 4 truncated anything
    longer in silence, version 5 raises, and neither is a good outcome: the
    first makes two different passwords interchangeable, the second turns a
    long password into a 500. Callers validate the length first; this is the
    backstop.
    """
    encoded = plain.encode("utf-8")
    if len(encoded) > MAX_PASSWORD_BYTES:
        raise ValueError(
            f"Password exceeds bcrypt's {MAX_PASSWORD_BYTES}-byte limit"
        )
    return bcrypt.hashpw(encoded, bcrypt.gensalt(rounds=12)).decode("utf-8")


def verify_password(plain: str, hashed: str) -> bool:
    """Verify a plaintext password against a bcrypt hash."""
    try:
        return bcrypt.checkpw(plain.encode("utf-8"), hashed.encode("utf-8"))
    except Exception:
        logger.exception("Password verification error")
        return False


def create_token(user_id: str, email: str, name: str) -> str:
    """Create a JWT token with user claims, valid for JWT_EXPIRY_HOURS."""
    now = datetime.now(timezone.utc)
    payload = {
        "sub": user_id,
        "email": email,
        "name": name,
        "iat": now,
        "exp": now + timedelta(hours=JWT_EXPIRY_HOURS),
    }
    return jwt.encode(payload, JWT_SECRET, algorithm=JWT_ALGORITHM)

OAuth state, signed and bound to the browser — actual source, backend/auth.py, create_state(), state_cookie(), verify_state_request()

A signed state on its own proves only that this application minted it — and /api/auth/oauth/<provider> hands a valid one to anybody who requests it. An attacker could therefore fetch a state and feed their own authorization code to the callback in a victim's browser, logging the victim into the attacker's account. The same value is also written to a short-lived HttpOnly cookie, and the callback requires the two to match; an attacker cannot set a cookie on this origin. This is the only cookie the application uses — the session token itself is not in a cookie, but in localStorage, sent as an Authorization: Bearer header. 

# backend/auth.py
def create_state() -> str:
    """Mint a short-lived signed OAuth `state` value.

    Signing it keeps the check stateless: the callback can tell its own
    redirect apart from one a third party initiated, without a session store.
    """
    now = datetime.now(timezone.utc)
    return jwt.encode(
        # `jti` makes every state unique.  Without it the payload is just
        # iat/exp, so two flows starting in the same second get byte-identical
        # states and the cookie check below would accept one flow's state in
        # another flow's browser.
        {"purpose": "oauth_state", "jti": secrets.token_urlsafe(16),
         "iat": now, "exp": now + timedelta(minutes=10)},
        JWT_SECRET, algorithm=JWT_ALGORITHM,
    )


OAUTH_STATE_COOKIE = "p3_oauth_state"
OAUTH_STATE_MAX_AGE = 600


def state_cookie(state: str) -> str:
    """Set-Cookie value binding `state` to the browser starting the flow."""
    parts = [
        f"{OAUTH_STATE_COOKIE}={state}",
        "Path=/",
        "HttpOnly",
        # Lax, not Strict: the provider redirects back by top-level navigation,
        # and Strict would withhold the cookie on that cross-site hop.
        "SameSite=Lax",
        f"Max-Age={OAUTH_STATE_MAX_AGE}",
    ]
    if os.environ.get("WEBSITE_INSTANCE_ID"):
        # Azure serves HTTPS; `func start` is plain HTTP, where Secure would
        # stop the cookie being stored at all.
        parts.append("Secure")
    return "; ".join(parts)


def verify_state_request(req) -> bool:
    """Check the OAuth `state`: signed by us, unexpired, and this browser's."""
    from_provider = req.params.get("state", "")
    if not verify_state(from_provider):
        return False
    from_cookie = read_cookie(req, OAUTH_STATE_COOKIE)
    if not from_cookie:
        logger.warning("OAuth callback carried no state cookie")
        return False
    if not secrets.compare_digest(from_provider, from_cookie):
        logger.warning("OAuth state did not match the state cookie")
        return False
    return True

Both callbacks call verify_state_request(req) as their first action and reject a bad or missing state before the authorization code is read or exchanged (backend/function_app.py, oauth_google_callback() and oauth_github_callback()). A rejection redirects to login.html?error=oauth_state rather than returning bare JSON at the Function App hostname, so the visitor is not stranded off the dashboard's origin with no way back (_oauth_error()).

6.2 What is still unproven, stated plainly

  • Nothing has been provisioned. deploy.sh creates a resource group, a storage account with the two containers, a serverless Cosmos account with users and cache containers, a Consumption-plan Python 3.11 Function App, the app settings and the static website upload, and then uploads All_Diets.csv to fire the trigger. It deliberately does not configure CORS at the platform layer: the application emits those headers itself on every response path, including the OPTIONS pre-flight and the 401 from the auth gate, and a response carrying Access-Control-Allow-Origin twice is rejected by every browser. That makes the FRONTEND_URL setting load-bearing — it is the origin the application echoes, and it falls back to * when unset. The script has not been run, and the repository contains no output from it.
  • The cached read path is unoptimized. get_recipes() pulls every chunk on every request and filters in Python; there is no server-side Cosmos query. This is correct but not necessarily fast, and it has never been timed.
  • Blob-trigger latency is unmeasured. A Consumption-plan blob trigger polls rather than subscribing to events, so the post-upload invocation can lag by minutes. Either switch to an Event Grid trigger or script the wait into the demo narration.
  • The JWT lives in localStorage and is delivered to the browser in a URL fragment after OAuth. That is simpler than an HttpOnly cookie and measurably weaker against XSS. It is a deliberate trade-off, not a solved problem, and earlier revisions of this report incorrectly claimed HttpOnly cookies were in use.
  • There is no rate limiting on the login endpoint. bcrypt at 12 rounds makes offline cracking of a stolen hash expensive, but it does not throttle online guessing.

Every cell value originates in the uploaded CSV, and clean_data normalises text without sanitising markup, so a crafted Diet_type or Recipe_name would otherwise break out of the row markup and read the session token out of localStorage. renderRecipeTable() passes every interpolated value through escapeHtml(), which assigns the value to a detached element's textContent and reads back its innerHTML — so the browser does the escaping. That closes a stored-XSS path through the dataset, which matters more here than usual because the token is script-reachable by design (§9).

1 CSV data quality Repeated recipe names and unusable numeric values. Measured on All_Diets.csv: 372 (diet, recipe name) pairs occur more than once, accounting for 662 extra rows — but only 91 of those rows repeat the same macro values. 284 of the groups carry different macros, so they are distinct extractions of the same dish, not duplicates. Diet-type casing is in fact already consistent in this file. Whitespace is stripped and diet and cuisine are case-folded defensively; macros are coerced to numeric, values that are negative or non-finite are discarded and replaced with the column mean, and the number of imputed values is recorded in df.attrs. Rows are deliberately not deduplicated: with 284 groups holding different macros, collapsing by name would discard real observations and shift every average. An earlier revision of this report claimed the cleaning step deduplicated — it does not, and should not (backend/nutrition.py:13-42). Implemented
2 A process-local cache is invisible to other instances On Azure Functions the blob trigger and the HTTP handlers are not guaranteed to share a process, so an in-memory cache leaves the API with nothing to serve — and search, filter and pagination then operate on whatever fallback exists. Recipes are persisted to Cosmos, mirroring the insights path, so any instance can read them (cache.py, store_recipes() and get_recipes()). Implemented
3 The dataset exceeds the Cosmos document limit A Cosmos document may not exceed 2 MB; the cleaned dataset serializes to roughly 1.2 MB and would break on any growth. Records are split into chunks of 2,000 with a recipes_meta document holding the count. Orphan chunks from a larger previous dataset are deleted before the new count is published, and a reader that finds a chunk missing discards the whole set rather than serving a partial one (cache.py: CHUNK_SIZE, store_recipes(), get_recipes()). Fallbacks are now opt-in via ENABLE_DEMO_FALLBACK, default off, and an empty cache returns 503 with an explanation. The dashboard status pill names the source on screen (function_app.py, _demo_fallback_enabled(); frontend/app.js, updateStatusBar()). Implemented
5 A client-side redirect is not access control The browser gate does not verify the token signature, so on its own it protects nothing. Implemented

Implemented

Implemented
8 Blob-trigger polling delay A Consumption-plan blob trigger polls rather than subscribing to events, so the invocation after an upload can lag by minutes — long enough to stall a live demo of “cleaning runs once per CSV change”. Nothing yet. The options are an Event Grid blob trigger or scripting the wait into the narration. Open
9 The deployed frontend could not reach the backend The frontend resolved its API base to a relative /api for any non-localhost host, but it is served from the storage account's $web static website, which has no /api reverse proxy — only Azure Static Web Apps provides one. Every data request would have returned 404 against the storage domain, and because the dashboard degrades quietly the result would have looked like an empty dashboard rather than an error. frontend/config.js resolves window.API_BASE from an __API_BASE__ placeholder; deploy.sh substitutes https://<function-app>.azurewebsites.net/api into a staging copy before upload and aborts if the substitution did not take, so a silent mis-deploy is not possible (frontend/config.js, deploy.sh, the frontend-upload step). Implemented
10 Indexing the cached payloads cost write RUs for nothing Cosmos indexes every path by default. Each chunk document holds a 2,000-element records array, and the insights document holds its aggregates under data — so every blob-trigger write was paying to index thousands of nested fields. No query reads them: chunks are fetched by id.
