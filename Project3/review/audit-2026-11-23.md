# Project 3 — code review, 2026-11-23

**Scope.** Static review of authentication, user persistence, and recipe-cache
write paths in the current working tree. No files were changed as part of the
review, and tests or Azure integration checks were not run.

## Findings

### P1 — Cosmos initialization failure silently switches accounts to memory

`backend/function_app.py:64-82` returns `None` both when Cosmos is not
configured and when Cosmos initialization fails. `_save_user()` then treats
both cases as the local-development path and writes to `_memory_users`
(`:129-149`). Registration can therefore return success even when a deployed
Function App has Cosmos settings but cannot connect to Cosmos. Since Functions
may route later requests to another process or instance, the account may be
unavailable at login or disappear when the process restarts.

**Suggested fix:** distinguish intentionally unconfigured local development
from configured-but-unavailable Cosmos. In the latter case, fail closed for
registration and login with a service error instead of claiming that the user
was durably saved.

### P2 — Public login and registration endpoints have no rate limiting

`backend/function_app.py:520-567` and `:574-609` expose registration and login
without a rate limit. Login runs bcrypt verification for an existing account
(`:592-597`), so repeated anonymous requests can consume substantial CPU; the
public registration endpoint also performs bcrypt hashing (`:547-552`).

**Suggested fix:** add request throttling at the gateway or application layer,
including per-IP limits and account-based backoff for repeated failed logins.

### P2 — Concurrent registrations can create duplicate accounts for one email

Registration checks for an existing email and then writes a `User` with a
random UUID (`backend/function_app.py:542-559`; `backend/models.py:12-15`).
Two requests can both pass the lookup before either write completes. Because
the Cosmos document ID is not derived from the normalized email, both upserts
can succeed as separate documents in the same email partition. Later email
lookups can then find an ambiguous account and password.

**Suggested fix:** enforce email uniqueness atomically in the persistence
layer, for example with a deterministic email-based document ID and create-only
semantics, and return a conflict when another request wins the race.

## Review note

This record captures code-level risks only. It does not establish whether the
application is currently deployed or whether its Azure settings and throttling
controls mitigate these issues.

## Verification of the findings (2026-11-23)

All three findings were confirmed against the code. The verification added
the following:

- **P1.** The failure was sticky: `_users_tried` kept the process on memory
  after one failed initialization. A failed Cosmos *query* in
  `_find_user_by_email` also fell back to memory, so the duplicate-email check
  could pass for an existing account.
- **P2, rate limiting.** `host.json` sets host-wide concurrency limits
  (`maxConcurrentRequests: 100`, `maxOutstandingRequests: 200`,
  `dynamicThrottlesEnabled`). These are not per-client limits. An unknown
  email skipped bcrypt, so response time revealed which addresses had
  accounts.
- **P2, duplicates.** Neither `deploy.sh` nor `_get_users()` sets a unique-key
  policy on the `users` container. Login read `items[0]` with no ordering. The
  OAuth create path had the same race, and OAuth emails were not lowercased
  the way registration lowercases them.

## Remediation (2026-11-23, commit `2ded6db` on branch `robin/p3-auth-hardening`)

| Finding | Change | Where |
|---|---|---|
| P1 | Cosmos *unconfigured* still means the in-memory dev store. Cosmos *configured but unreachable* raises `UserStoreUnavailable`: register and login return 503, the OAuth callback redirects with `account_not_saved`, and `/api/health` reports `degraded` / `Cosmos DB (unavailable)`. Failed lookups are no longer read as "no such user", and a failed durable write is no longer copied into memory. Initialization is retried after 30 s instead of never. | `backend/function_app.py` (`_get_users`, `_find_user_*`, `_save_user`, `health_check`) |
| P2 duplicates | New accounts get `User.id_for_email()` (UUIDv5 of the normalized email) and are written with `create_item`. A conflict returns 409. The memory store does the same check-and-insert under a lock. OAuth creation uses the same path and lowercases the email. Legacy duplicate documents resolve to the oldest. | `backend/models.py`, `backend/function_app.py` (`_create_user`, `register`, `_handle_oauth_user`) |
| P2 rate limiting | Sliding-window limits: login 20 per client address per 5 min, registration 10 per address per hour, and an account lock after 5 wrong passwords in 15 min. The lock is checked before bcrypt and cleared on success. Blocked requests get 429 with `Retry-After`. The client address is the right-most `X-Forwarded-For` entry. An unknown email or a password-less OAuth account spends one bcrypt check on a dummy hash. | `backend/ratelimit.py` (new), `backend/function_app.py` |

**Re-review.**

- The full suite passes: 171 tests, 28 of them new in
  `tests/test_user_store.py` (log: `docs/evidence/tests.log`).
- Against the pre-fix code, the 18 new tests that target these findings fail.
  The other 10 cover the new `ratelimit` module.
- `flake8` is clean.
- An end-to-end run with real bcrypt took about 170 ms for each of an unknown
  email, a wrong password and a correct password.

**Remaining limits.**

- Throttling counters are per worker process. A scaled-out app counts each
  instance separately, and a restart clears the counters. A global limit
  needs Front Door / API Management or a shared store.
- The per-account lock could be triggered deliberately to lock a user out
  for 15 minutes. *Replaced in the follow-up below.*
- Duplicate documents written before this change are not cleaned up, only
  resolved deterministically. Existing accounts keep their random ids.
- Nothing was deployed or tested against Azure.

## Follow-up review (2026-11-24)

A second pass over the remediation found five more issues. All were confirmed
against the code and fixed on the same branch.

| # | Finding | Fix |
|---|---|---|
| 1 (P1) | `_cosmos_users_configured()` treated "only one of `COSMOS_ENDPOINT` / `COSMOS_KEY` set" as unconfigured, so a half-configured deployment still registered accounts into memory. | `_cosmos_users_config()` returns `configured`, `unconfigured` (both unset) or `partial`. `partial` raises `UserStoreUnavailable` (503) and is logged as a configuration error. Only the complete absence of both settings means local development. |
| 2 (P2) | Anyone who knew an email could lock its owner out for 15 minutes with five wrong passwords. | The hard per-account lock is gone. Password attempts are limited to 5 per (account, client address) pair per 15 min, so one source can only block itself. Guessing spread over many addresses meets a cap of 50 per account per 15 min, which does not apply to addresses that have completed a login to that account in the last 30 days. |
| 3 (P2) | `retry_after()` ran before bcrypt and `record()` after it, so concurrent requests could all pass the check. | `SlidingWindowLimiter.reserve()` checks and counts in one locked step before bcrypt runs, and `release()` refunds the attempt on success or when the store is down. At most `limit` password checks are admitted, however many requests are in flight. |
| 4 (P2) | `link()` in `_handle_oauth_user` ignored `_save_user()`, so a sign-in could succeed with the provider link never stored. | `link()` returns the save result, and both call sites return `account_not_saved` without issuing a token when it is `False`. |
| 5 | This record said the remediation was in the uncommitted working tree. | The heading now names the commit and branch. |

**Re-review.**

- The full suite passes: 181 tests (`docs/evidence/tests.log`).
- `tests/test_user_store.py` now has 38 tests. Against the code at the
  previous commit, the 11 tests for these five issues fail.
- The concurrency tests passed on five repeated runs. `flake8` is clean.
- With real bcrypt, an attacker's address got five 401s and then a 429, while
  the owner still signed in from their own address. Fifteen concurrent wrong
  guesses from one address produced five password checks and ten 429s.

**Remaining limits.**

- Counters and trusted sources are still per worker process, so the earlier
  scale-out and restart caveat applies to them too.
- During a distributed attack, an owner signing in from an address that has
  never signed in to the account can be refused until the window passes.
  Removing that would need a second factor or a CAPTCHA, which this project
  does not have.
