## 1. 结论摘要

1. **得分完全由截图证据决定**：11 个子任务各 5 分，共 55 分。每个子任务都有明确的截图清单，且**所有截图必须能看到日期和时间**，这是最容易整体丢分的一条。
2. **实际数据集与讲义不符**（最关键的发现）：讲义按逐条行程数据（`Date/Time` 列，精确到分钟）来写代码；而 Brightspace 提供的文件是**按日期 + 调度基地汇总的数据**，列为 `dispatching_base_number,date,active_vehicles,trips`，只有日期，没有时刻。
   - 直接照抄讲义代码会报 `KeyError: 'Date/Time'`。
   - 改为使用 `date` 列后，`Hour` 全部为 0，"按小时统计、高峰小时、星期×小时热力图"会失去意义。
   - 每一行代表的是"某基地某天的行程总数"，因此统计必须**以 `trips` 列加权**，不能用 `.size()` 数行数，否则结论是错的。
3. **已有代码大体可用，但有 6 处会直接影响得分或运行**（见第 4 节）。其中最严重的三处：Dockerfile 用的是 `python:3.11-slim`，而讲义要求 Python 3.8 slim；JMeter 的 CSV 配置没有跳过表头，会产生错误请求；缓存 key 被哈希化，截图中看不出"以 timestamp 为 key"。
4. **本机是 Apple Silicon（`uname -m` 输出为 `arm64`）**：在本机或本机上的 Ubuntu 虚拟机中构建的镜像默认是 arm64，推送后在 Azure x86 VM 上运行会报 `exec format error`。必须用 `docker buildx --platform linux/amd64` 构建。
5. **Task 3.2（VMSS 扩缩容）和 Task 5.1（性能对比）是耗时最长、失败风险最高的部分**：
   - 只有持续负载才能触发 Azure 自动扩缩容：平均 CPU 需在 5–10 分钟窗口内超过 70%，触发后还有冷却期。现有的 JMeter 计划（500 线程 × 5 次循环）只能持续不到 2 分钟，不足以触发扩容。
   - 数据集只有 354 行，单次"预测"计算本来就很便宜，Redis（尤其是跨网络、走 TLS 的 Azure Redis）带来的响应时间收益可能很小，甚至为负。性能对比必须如实呈现，并给出解释。
   - Azure Monitor 的 VM/VMSS 内置指标**没有"响应时间"**，需要用 JMeter 的结果或 Application Insights 来补充。

## 3. 数据集分析（实测结果）

| 项目 | 结果 |
|---|---|
| 行数 | 354 行（无缺失值、无重复行，所以 dropna 和去重后仍为 354 行） |
| 列 | `dispatching_base_number`、`date`（格式 `M/D/YYYY`）、`active_vehicles`、`trips` |
| 时间范围 | 2015-01-01 至 2015-02-28，共 59 天 |
| 基地数 | 6 个 |
| 总行程数（按 trips 加权） | **4,130,230** |
| 最忙的一天 | **2015-02-20（周五），100,915 次**；其次是 02-14（情人节，周六）100,345 次、02-21（周六）98,380 次 |
| 最少的一天 | **2015-01-27，25,244 次**（与 2015 年 1 月 26–27 日纽约暴风雪及交通禁令时间吻合，可作为异常值说明） |
| 最大基地 | B02764，1,914,449 次（约占 46%） |
| 星期日均行程 | 周六 83,481 > 周五 79,021 > 周四 73,961 > 周三 66,408 > 周日 65,493 > 周二 60,383 > 周一 57,975 |
| 周末效应 | 周六最高，周日接近工作日中段水平，即"周五、周六夜间出行高峰"模式 |
| 小时维度 | **不可用**：没有时刻信息，`Hour` 全为 0 |

**报告中的处理方式（如实说明，不编造小时数据）**
- 照讲义结构生成 `Hour` 等特征，并在报告中写明：所提供的数据集是按天汇总的，因此 Hour 恒为 0，"高峰小时"无法从该数据集得出。
- 按讲义代码生成的热力图只有 1 列（Hour = 0），照样截图；同时补充一张**有信息量**的替代热力图：星期 × 基地（或星期 × 周序号），以 trips 加权。这样既满足"有热力图"的要求，也体现对数据的理解。
- "busiest day" 用 `groupby('Day')['trips'].sum().idxmax()`；"peak hours" 用同样的方法得出 hour 0，并附说明。另外给出"高峰星期几"（Saturday）作为可解释的替代指标。

## 4. 现有代码审查

| # | 文件 | 问题 | 影响 | 处理建议 |
|---|---|---|---|---|
| 1 | `Dockerfile` | 基础镜像是 `python:3.11-slim`，讲义要求 **Python 3.8 slim** | 2.1 的评分点不符，可能扣分 | 改为 `python:3.8-slim`；同时把依赖降到兼容 3.8 的版本（pandas 2.2.2 要求 Python ≥ 3.9，需改用 pandas 2.0.3） |
| 2 | `requirements.txt` | 缺少 `matplotlib`、`seaborn`（1.2 中画图要用） | 讲义要求列出"所有必要的包"，评分者可能对照 `app.py` 的 import 检查 | 补上这两个包，并固定与 3.8 兼容的版本 |
| 3 | `jmeter_test_plan.jmx` | CSV Data Set 设置了 `variableNames`，但没有设置 `ignoreFirstLine=true` | CSV 表头行会被当成数据，发出 `timestamp=date` 的请求并返回 400，Summary 中 Error % 不为 0 | 加上 `ignoreFirstLine=true` |
| 4 | `jmeter_test_plan.jmx` | 500 线程 × 5 次循环 = 2,500 个请求，1 分钟左右就跑完 | 足够应付 1.3，但不足以触发 VMSS 扩容（3.2）或产生可对比的 Monitor 曲线（5.1） | 另建一个"持续负载"版本：开启 Scheduler，Duration 设为 15–20 分钟，循环次数设为无限；服务器地址参数化为 `${__P(host,localhost)}` |
| 5 | `app.py` | 缓存 key 是 `uber:prediction:<sha256>` | 讲义要求"以请求 timestamp 作为 key"，redis-cli 截图中看不出 timestamp | 改为 `predict:<timestamp>` 这样可读的 key |
| 6 | `app.py` | Redis 只能通过 `REDIS_URL` 配置；没有连接超时；`get`/`setex` 出错时没有降级处理 | 讲义 4.2 给出的是 host/port/password/ssl 写法，评分者会对照；连不上 Azure Redis 时请求可能挂起或返回 500，且难以察觉缓存其实没生效 | 改为环境变量 `REDIS_HOST/PORT/PASSWORD/SSL`，按讲义形式构造 `redis.Redis(...)`；设置 `socket_connect_timeout`/`socket_timeout`；异常时降级为直接计算；在响应或健康检查中显示 `cache: enabled/disabled` |
| 7 | `app.py` | `predict()` 按 Hour 匹配，而 Hour 恒为 0：timestamp 的小时为 0 时返回所有行的均值，不为 0 时走 fallback，结果完全一样 | 预测与输入几乎无关，在报告中缺乏说服力 | 改为"同星期几（或同一天）+ 同基地的历史日均行程"，让不同 timestamp 得到不同结果 |
| 8 | `app.py` | 1.2 的画图代码（`plt.show()`）不在 `app.py` 中；讲义要求"Add into your app.py" | 提交的 `app.py` 与截图内容对不上 | 加入 `run_analysis()`，通过 `python app.py --analyze` 触发，图片保存为 PNG（有 GUI 时也可 show）；Flask 服务模式下不执行画图 |
| 9 | `docker-compose.yml` | 本身没问题，可解决"容器内的 localhost 不是宿主机 Redis"的问题 | 讲义 4.1 用的是 `docker run -d -p 6379:6379 redis`。如果 app 也跑在容器里，并用 `localhost` 连接，就连不上 Redis，`get_redis()` 会静默返回 None，导致永远看不到 `source: cache` | 4.1 推荐用 compose，或者用 `docker network` 让 app 与 redis 处于同一网络；也可以直接在 VM 中用 `python3 app.py` 本地运行 |

`report.html` 中的统计数字（4,130,230、02-20 / 100,915、B02764 / 1,914,449）与本次实测一致，可以继续使用。但它还没有放入任何实际截图，最终仍需导出为 PDF。

## 5. 风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| CPU 架构不匹配 | 本机为 arm64；Azure 常见的 B 系列 VM 是 x86_64 | 用 `docker buildx build --platform linux/amd64 -t <user>/uber-app:latest --push .`；在 VM 上用 `docker image inspect` 确认 Architecture 为 amd64 |
| VMSS 扩容难以触发 | 自动扩缩容基于平均 CPU，默认时间窗口 10 分钟，加上冷却时间，一轮扩缩容大约需要 15–25 分钟；B1s 单核机器配 gunicorn 两个 worker，请求很轻，未必能把 CPU 压到 70% | 用小规格实例（如 B1s）；持续 15 分钟以上的高并发 JMeter 负载；把规则时间窗口设为 5 分钟；必要时让 `/predict_traffic` 增加一个可选的 `?work=N` 参数做可控的 CPU 负载，仅用于压测，并在报告中说明 |
| 沙盒限制 | Azure 沙盒或学生订阅通常限制区域、VM 规格、vCPU 配额，资源组可能是预先创建的 | 先在 Portal 中确认可用区域和配额；VMSS 最大实例数设为 2–3 |
| Azure Cache for Redis 能否创建 | 微软已公布 Azure Cache for Redis 向 Azure Managed Redis 迁移的计划，新建 Basic C0 在部分订阅中可能受限（**需在 Portal 中实际确认**）；即使可以创建，部署也需要 15–20 分钟；新实例可能默认关闭"访问密钥认证" | 尽早创建；如果 Basic C0 无法创建，截图记录报错，改用 Azure Managed Redis 最小规格，并在报告中说明；确认 Access keys 已启用 |
| Azure Redis 的连接 | 端口 6380 必须 `ssl=True`；6379 默认关闭 | 代码中的连接参数通过环境变量注入，主密钥不要写进提交的代码 |
| 缓存收益不明显 | 数据量很小，计算成本低；远程 Redis 每次请求要多一次网络往返 | 5.1 如实对比，重点看 CPU 和扩缩容次数的变化；响应时间结合 JMeter 的前后两次 Summary 来比较 |
| 响应时间指标来源 | VM/VMSS/Load Balancer 的内置指标都没有 HTTP 延迟 | 方案 A：JMeter Summary 前后对比，并截 Azure Monitor 的 CPU 图；方案 B：接入 Application Insights（OpenTelemetry），可以在 Azure Monitor 中直接得到服务端响应时间 |
| 凭据泄露 | Redis 主密钥、Docker Hub 凭据 | 只放在 VM 的环境变量或 `.env` 文件中（权限 600），不提交、不出现在截图里；截图前遮挡 Access keys 页面 |
| 截图缺少时间 | 会被整体质疑真实性 | 每张截图都包含系统时钟，或终端中的 `date` 输出 |

## 6. 建议执行顺序与时间预估

1. 本地：修正代码（Python 3.8 镜像、key、Redis 配置、JMeter）→ 1.1 / 1.2 / 1.3 / 2.1 / 2.2 / 4.1（约 2–3 小时）

> 注意：讲义的顺序是 3.2 → 4.x → 5.1，但 5.1 需要"缓存前"的数据。因此在 3.2 压测时就要把"无缓存"的时间段和 JMeter 结果记录下来，否则之后还要关掉缓存重测一次。
