阶段 0

装工具、登录

~15 分钟

装三个工具

Phase 2 比 Phase 3 多一个依赖：前端走 Azure Static Web Apps，需要 swa CLI。缺了它脚本不会崩，但会跳过前端上传并打印警告 —— 那样 Integration 的 20 分就拿不到。

# Azure CLI（Ubuntu / Debian）
curl -sL https://aka.ms/InstallAzureCLIDeb | sudo bash

# Functions Core Tools v4 和 Static Web Apps CLI（都要 Node.js）
npm i -g azure-functions-core-tools@4 --unsafe-perm true
npm i -g @azure/static-web-apps-cli

# 三个都要有输出
az version --output table
func --version
swa --version

swa --version 没输出就别往下走。 先把它装上，否则阶段 2 跑完你会得到一个能用的 API 和一个没上线的前端。

登录并确认订阅

az login
az account show --query "{订阅:name, 订阅ID:id, 用户:user.name}" -o table

有多个订阅的话，确认这里显示的是你想计费的那个。切换：az account set --subscription "订阅名"。

阶段 1

定名字

~3 分钟

为什么要先定。 Function App 和存储账号的名字是 Azure 全局唯一的，默认值大概率已被占用，脚本会在创建时报一个很难看懂的错。先加后缀定下来，顺带你也知道了最终的 URL 长什么样。

导出名字，算出最终 URL

# 把 yy 换成你的缩写，只能小写字母、数字、连字符
export FUNCTION_APP_NAME=cpsy300-nutrition-api-yy
export STATIC_WEB_APP_NAME=cpsy300-nutrition-dash-yy

echo "部署完 API 会在："
echo "  https://${FUNCTION_APP_NAME}.azurewebsites.net/api/health"

这个终端别关。 阶段 2 要用到这两个 export。关了就重跑这一步。

先确认名字没被占

az functionapp list --query "[?name=='$FUNCTION_APP_NAME'].name" -o tsv
# 没有任何输出 = 你的订阅里没有同名的，可以继续
阶段 2

部署

~15 分钟

跑 deploy.sh

必须先进到 Project2 目录再跑 —— 脚本里的数据集路径和 backend/ 都是相对路径。

cd ~/Desktop/claude-computing/Project2
chmod +x deploy.sh
./deploy.sh

脚本一共 7 步，会自己走完：资源组 → 存储账号并上传 CSV → Function App 和应用设置 → 发布后端 → 创建 Static Web App → 把真实 API 地址注入前端再上传 → 把 CORS 收窄到前端域名并冒烟测试三个端点。

最后应该看到。 三行 OK 的冒烟测试，以及打印出来的 Function App 和 Dashboard 两个地址。第一次调用要等冷启动，脚本给了 180 秒超时，慢是正常的。

Static Web App 在 eastus2，其他资源在 eastus —— 这不是写错了，SWA 在 eastus 不提供服务。脚本已经处理好了。

把两个真实地址记下来

export API_URL="https://${FUNCTION_APP_NAME}.azurewebsites.net"
export DASH_URL="https://$(az staticwebapp show --name "$STATIC_WEB_APP_NAME" \
  --resource-group cpsy300-nutritional-insights-rg --query defaultHostname -o tsv)"

echo "API:       $API_URL"
echo "Dashboard: $DASH_URL"
阶段 3

验证真的成功了

~5 分钟

这一步别跳。 前端在拿不到 API 时会自动降级成离线模式并显示黄色横幅，用的是 Project 1 的真实批处理结果。页面照样好看、图表照样有数据 —— 但那不是云上来的，Integration 的 20 分会丢。所以必须确认它走的是在线路径。

三个端点都要通

curl -s "$API_URL/api/health" | python3 -m json.tool

# 真实数字核对：total_recipes 必须是 7806
curl -s "$API_URL/api/insights" | python3 -c "import sys,json; d=json.load(sys.stdin); print('总数', d['summary']['total_recipes']); print('各 diet', d['summary']['diet_counts']); print('耗时(秒)', d['metadata']['execution_time_seconds'])"

# 分页：应该是 7806 条、157 页、本页 50 条
curl -s "$API_URL/api/recipes?page=1&limit=50" | python3 -c "import sys,json; d=json.load(sys.stdin); print('total',d['total'],'pages',d['total_pages'],'本页',d['count'])"

各 diet 的正确数字（跟你本地一致才说明云上读的是同一份数据）：mediterranean 1753、dash 1745、vegan 1522、keto 1512、paleo 1274。

打开仪表盘，确认不是离线模式

echo "$DASH_URL"

浏览器打开这个地址，检查三件事：

看哪里成功失败
右上角徽章绿色 API Connected橙色 Offline - fallback data
页面顶部没有黄色横幅黄色「离线模式」横幅
控制栏右侧Source: Azure Blob Storage (live)Source: offline fallback

如果是离线模式，99% 是 CORS 或 API 地址注入失败。按 F12 看 Console：报 CORS 就重跑脚本第 7 步；报 404 就检查 curl $API_URL/api/health 是否真的通。排错清单在页面最后。

顺手留一份命令行证据

截图之外，纯文本的 curl 输出是最干净的证据，PDF 里贴一段很有说服力。

回填 URL、导出 PDF

~10 分钟

把占位符换成真实地址

仓库里现在是 <function-app> 这类占位符 —— 这是故意的，没部署就写死地址就是造假。现在可以换了。

cd ~/Desktop/claude-computing/Project2
grep -rn "<function-app>\|<static-web-app>" README.md docs/ | head -20
# 逐处换成 $API_URL / $DASH_URL 的真实值

填九个截图占位，导出 PDF

cd ~/Desktop/claude-computing/Project2
grep -n "PENDING SCREENSHOT" docs/Phase2-Documentation.md

然后导出 PDF（任选一种）：

# 方式 A：VS Code 装 Markdown PDF 扩展，右键 Export (pdf)

删光资源（省钱）

~2 分钟

跑 teardown.sh

脚本会先列出要删的资源、要你确认，再删整个资源组。
