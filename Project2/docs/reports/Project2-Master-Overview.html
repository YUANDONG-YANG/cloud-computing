What the CI pipeline does and does not do

CI is split into one workflow per phase. .github/workflows/deploy.yml runs the Phase 1 local-simulation job: it builds the Docker image, runs pytest and flake8, and exercises the Azurite-based local simulation. .github/workflows/project2-tests.yml runs the Phase 2 project2-tests job: on Python 3.11 it installs Project2/requirements-dev.txt, runs python -m pytest -q against Project2/tests/ (test_function_app.py, test_nutrition.py, test_frontend_demo_data.py), runs flake8 ., and syntax-checks the deployment script with bash -n deploy.sh. Neither job deploys anything to Azure. There is no azure/functions-action step, no Azure/static-web-apps-deploy step and no Azure credentials or publish profile in the workflow. Deployment is a deliberate manual step so that no subscription secrets are needed in CI.

Architecture Components

Static Web AppServes the dashboard as plain static files. Charts are drawn with Chart.js 4.4.1 plus a CSS-grid heatmap built in app.js. staticwebapp.config.json adds a navigation fallback and the X-Content-Type-Options, X-Frame-Options and Referrer-Policy headers.
Function AppThree anonymous HTTP GET routes registered with the Azure Functions v2 decorator model. Reads the CSV from Blob Storage, cleans it with the shared nutrition.py module, and returns JSON. The cleaned DataFrame is cached by blob ETag.
Blob StorageA private datasets container holding All_Diets.csv (7,806 recipes). Public blob access is disabled and the minimum TLS version is 1.2. The connection string lives only in Function App settings.
GitHub ActionsContinuous integration only: pytest, flake8 and a bash -n syntax check of deploy.sh. No Azure deployment job and no subscription secrets. Azure resources are created by running deploy.sh manually.

3. Cloud Setup & Configuration

Every command in this section is the one deploy.sh actually runs. The script is idempotent (set -euo pipefail, re-running updates existing resources) and runs in seven numbered steps. It has not been executed against a real subscription yet.

3.2 Storage Account and dataset upload — step 2 of 7

Azure Blob Storage Setup

Storage account names are globally unique, so the script reuses an existing cpsy300nutrition* account in the resource group when re-run and otherwise generates cpsy300nutrition$(openssl rand -hex 3). The container is private: public blob access is disabled at the account level and TLS 1.2 is the floor.

STORAGE_ACCOUNT="cpsy300nutrition$(openssl rand -hex 3)"   # e.g. cpsy300nutrition4f9a21
BLOB_CONTAINER="datasets"

az storage account create \
    --name "$STORAGE_ACCOUNT" \
    --resource-group "$RESOURCE_GROUP" \
    --location "$LOCATION" \
    --sku Standard_LRS \
    --kind StorageV2 \
    --min-tls-version TLS1_2 \
    --allow-blob-public-access false \
    --output none

CONN_STRING=$(az storage account show-connection-string \
    --name "$STORAGE_ACCOUNT" --resource-group "$RESOURCE_GROUP" \
    --query connectionString --output tsv)

az storage container create \
    --name "$BLOB_CONTAINER" \
    --connection-string "$CONN_STRING" \
    --output none

az storage blob upload \
    --container-name "$BLOB_CONTAINER" \
    --file "../Project1/data/All_Diets.csv" \
    --name "All_Diets.csv" \
    --connection-string "$CONN_STRING" \
    --overwrite \
    --output none

Secret handling: $CONN_STRING is never echoed. It is passed straight into the Function App settings, and the summary at the end of the script prints only the az functionapp config appsettings list command needed to retrieve it later.

3.5 CORS scoping and smoke test — step 7 of 7

CORS is scoped to exactly one origin

Step 7 first removes any * wildcard left behind by an earlier run, then allows only the Static Web App origin. It finishes by calling all three endpoints with curl -fsS --max-time 180, which both verifies the deployment and absorbs the cold start.

az functionapp cors remove \

az functionapp cors add \
    --name "$FUNCTION_APP_NAME" --resource-group "$RESOURCE_GROUP" \
    --allowed-origins "$DASHBOARD_URL" --output none

for endpoint in health "insights" "recipes?page=1&limit=5"; do

5.1 Azure Function — v2 programming model (backend/function_app.py)

There is no function.json anywhere in this project. Routes are declared in Python with the v2 decorator model: a single func.FunctionApp object with one @app.route(...) per endpoint. The api prefix comes from host.json, so the routes resolve as /api/health, /api/insights and /api/recipes.

"""Azure Functions v2 HTTP API for Nutritional Insights Dashboard.

Endpoints:
    GET /api/health   -- liveness check (no storage call)
    GET /api/insights -- average macros, top recipes, common cuisines, summary stats
    GET /api/recipes  -- recipe rows; optional ?diet_type=, ?page=, ?limit=

CORS is configured at the Function App host level (see deploy.sh), so this
module deliberately does not emit Access-Control-Allow-* headers itself --
doing both produces duplicate headers, which browsers reject.
"""
import io, json, logging, os, threading, time

import azure.functions as func
import pandas as pd
from azure.storage.blob import BlobServiceClient

from nutrition import average_macros, clean_data, common_cuisines, top_recipes

app = func.FunctionApp(http_auth_level=func.AuthLevel.ANONYMOUS)

DEFAULT_PAGE_SIZE = 50
MAX_PAGE_SIZE = 500

RESPONSE_COLUMNS = ["Diet_type", "Recipe_name", "Cuisine_type",
                    "Protein(g)", "Carbs(g)", "Fat(g)"]

# Cleaned dataset cache, keyed by the blob ETag so a re-uploaded CSV is picked
# up automatically. A worker handles requests concurrently, hence the lock.
_cache = {"etag": None, "frame": None}
_cache_lock = threading.Lock()


def _load_dataset():
    """Return the cleaned dataset, downloading from Blob Storage on a cache miss.

    The blob ETag is checked on every request (a cheap metadata call) and the
    CSV is only re-downloaded and re-cleaned when it has actually changed.
    """
    container = os.environ.get("BLOB_CONTAINER_NAME", "datasets")
    blob_name = os.environ.get("BLOB_NAME", "All_Diets.csv")

    client = BlobServiceClient.from_connection_string(_get_connection_string())
    try:
        blob_client = client.get_blob_client(container=container, blob=blob_name)
        etag = blob_client.get_blob_properties().etag

        with _cache_lock:
            if _cache["etag"] == etag and _cache["frame"] is not None:
                return _cache["frame"], True

        data = blob_client.download_blob().readall()
        frame = clean_data(pd.read_csv(io.BytesIO(data)))

        with _cache_lock:
            _cache["etag"] = etag
            _cache["frame"] = frame
        return frame, False
    finally:
        client.close()


def _error_response(message, status_code=500):
    """Return a JSON error response.

    Internal exception text is logged, never returned, so storage details
    cannot leak to the browser.
    """
    return _json_response({"error": message}, status_code)


@app.route(route="health", methods=["GET"])
def health(req: func.HttpRequest) -> func.HttpResponse:
    """Liveness check. Does not touch storage, so it stays fast and cheap."""
    return _json_response({
        "status": "healthy",
        "service": "nutritional-insights-api",
        "version": "2.0.0",
        "dataset_cached": _cache["frame"] is not None,
    })


@app.route(route="insights", methods=["GET"])
def insights(req: func.HttpRequest) -> func.HttpResponse:
    """Return aggregate nutritional insights: averages, top recipes, common cuisines."""
    start = time.time()
    try:
        df, cache_hit = _load_dataset()

        avg = average_macros(df)                       # mean macros per diet
        top = top_recipes(df)                          # top 5 by protein per diet
        cuisine_records = common_cuisines(df).to_dict(orient="records")
        totals = df.groupby("Diet_type")["Protein(g)"].sum()
        diet_counts = {str(k): int(v) for k, v in df["Diet_type"].value_counts().items()}
        ...
        return _json_response({
            "average_macros": avg_records,
            "top_recipes": top_records,
            "common_cuisines": cuisine_records,
            "total_protein_by_diet": total_records,
            "summary": summary,
            "metadata": {
                "execution_time_seconds": round(time.time() - start, 3),
                "source": "Azure Blob Storage",
                "dataset": os.environ.get("BLOB_NAME", "All_Diets.csv"),
                "dataset_from_cache": cache_hit,
            },
        })
    except Exception:
        logging.exception("Error in /api/insights")
        return _error_response("Failed to compute insights from the dataset.")

5.2 Server-side pagination (/api/recipes)

The full recipe payload for all 7,806 rows is about 1.21 MB of JSON, so /api/recipes pages on the server. limit defaults to 50 and is clamped to MAX_PAGE_SIZE = 500; page is clamped to the last available page; a non-numeric or non-positive value returns HTTP 400; an unknown diet_type returns HTTP 404. The response carries the paging metadata the frontend needs to draw its page buttons.

@app.route(route="recipes", methods=["GET"])
def recipes(req: func.HttpRequest) -> func.HttpResponse:
    """Return a page of recipe rows, optionally filtered by diet_type.

    Query parameters:
        diet_type -- filter to one diet ("all" or omitted returns every diet)
        page      -- 1-based page number (default 1)
        limit     -- rows per page, capped at MAX_PAGE_SIZE (default 50)
    """
    start = time.time()
    try:
        page = _positive_int(req.params.get("page"), 1)
        limit = _positive_int(req.params.get("limit"), DEFAULT_PAGE_SIZE, MAX_PAGE_SIZE)
    except ValueError as exc:
        return _error_response(f"Invalid pagination parameter: {exc}", 400)

    try:
        df, cache_hit = _load_dataset()

        diet_type = req.params.get("diet_type")
        if diet_type and diet_type.lower() != "all":
            df = df[df["Diet_type"].str.lower() == diet_type.lower()]
            if df.empty:
                return _error_response(f"No recipes found for diet type: {diet_type}", 404)

        total = len(df)
        total_pages = max(1, -(-total // limit))        # ceiling division
        page = min(page, total_pages)
        offset = (page - 1) * limit

        records = df[RESPONSE_COLUMNS].iloc[offset:offset + limit].to_dict(orient="records")

        return _json_response({
            "recipes": records,
            "count": len(records),
            "total": total,
            "page": page,
            "limit": limit,
            "total_pages": total_pages,
            "diet_type_filter": diet_type or "all",
            "metadata": {...},
        })
    except Exception:
        logging.exception("Error in /api/recipes")
        return _error_response("Failed to read recipes from the dataset.")

5.3 Frontend fetch and offline fallback (frontend/app.js)

The API base URL is read from window.NUTRITIONAL_API_URL, which index.html sets from the build-time placeholder. If /api/insights or /api/recipes fails, the whole dashboard switches to offline mode and renders the committed Project 1 batch results behind a prominent banner — live and fallback data are never mixed in one view.

// The deployed Function endpoint is injected by index.html via
// window.NUTRITIONAL_API_URL. "/api" only works when the dashboard and the
// Function are served from the same origin.
const API_BASE_URL = String(window.NUTRITIONAL_API_URL || "/api").replace(/\/+$/, "");

async function apiGet(path) {
    const response = await fetch(`${API_BASE_URL}${path}`);
    if (!response.ok) throw new Error(`API returned ${response.status}`);
    return response.json();
}

const fetchHealth   = () => apiGet("/health");
const fetchInsights = () => apiGet("/insights");

function fetchRecipes(dietType, page) {
    const params = new URLSearchParams({ page: String(page), limit: String(ROWS_PER_PAGE) });
    if (dietType && dietType !== "all") params.set("diet_type", dietType);
    return apiGet(`/recipes?${params.toString()}`);
}

async function loadData(dietType, page = 1) {
    hideError();
    setLoadingAll(true);

    let health = null;
    try { health = await fetchHealth(); }
    catch (err) { console.warn("Health check failed:", err.message); }

    try {
        const data = await fetchInsights();
        const recipesResp = await fetchRecipes(dietType, page);

        insightsData = data;
        isOffline = false;

        recipeState.rows       = recipesResp.recipes || [];
        recipeState.page       = recipesResp.page || 1;
        recipeState.totalPages = recipesResp.total_pages || 1;
        recipeState.total      = recipesResp.total ?? recipeState.rows.length;
        recipeState.serverPaged = true;                 // paging served by the Function

        updateApiStatus(true, health);
        updateExecTime(data.metadata?.execution_time_seconds);
        setOfflineBanner(null);
        $("#data-source-label").textContent = "Source: Azure Blob Storage (live)";
    } catch (err) {
        console.warn("API unavailable, using offline fallback:", err.message);
        insightsData = DEMO_DATA;                       // Project 1 batch results
        isOffline = true;
        loadOfflineRecipes(dietType, 1);

        updateApiStatus(false, health);
        updateExecTime(null);
        setOfflineBanner(`Could not reach ${API_BASE_URL} (${err.message}).`);
        $("#data-source-label").textContent = "Source: offline fallback";
    }

    renderAll(dietType);
    setLoadingAll(false);
}

CORS Configuration

One layer of CORS, scoped to one origin

CORS is handled only at the Function App host level. deploy.sh step 7 removes any * wildcard from an earlier run and then allows the Static Web App origin alone. backend/function_app.py deliberately emits no Access-Control-Allow-* headers of its own: if the host and the application both set them the browser receives duplicate headers and rejects the response, so the application layer stays out of it. The design decision is recorded in the module docstring.

az functionapp cors remove \
  --name cpsy300-nutrition-api \
  --resource-group cpsy300-nutritional-insights-rg \
  --allowed-origins "*" --output none 2>/dev/null || true

az functionapp cors add \
  --name cpsy300-nutrition-api \
  --resource-group cpsy300-nutritional-insights-rg \
  --allowed-origins "$DASHBOARD_URL"

The dashboard sends no custom request headers, so no preflight is triggered and no route needs to accept OPTIONS. Not yet verified in Azure — the configuration is committed but cannot be confirmed from a browser until the deployment is actually run.

API Endpoints

EndpointMethodParametersResponse
/api/healthGETNonestatus, service, version (2.0.0) and dataset_cached. Touches no storage, so it stays fast and cheap and works even if the blob is unreachable.
/api/insightsGETNoneaverage_macros, top_recipes (top 5 by protein per diet), common_cuisines, total_protein_by_diet, summary (totals, diet counts, highest mean/total protein) and metadata (execution_time_seconds, dataset_from_cache). About 5.8 KB of JSON.
/api/recipesGET?diet_type=<diet>&page=<n>&limit=<n> — all optional. limit defaults to 50 and is capped at 500; page defaults to 1 and is clamped to the last page; diet_type=all or omitted returns every diet.Paged recipe rows plus count, total, page, limit, total_pages, diet_type_filter and metadata. Invalid paging returns HTTP 400; an unknown diet returns HTTP 404.

These three routes are the whole API surface. There is no clustering, segmentation or machine-learning endpoint in this project.

Why paging exists, and what the cache saves

Serialising all 7,806 cleaned rows produces roughly 1.21 MB of JSON, which is slow to transfer on a cold Consumption-plan instance and visibly janky to render as table rows. With the default limit=50 a page is about 1/156th of that. The ETag-keyed cache is the second half of the same idea: the CSV is downloaded and cleaned once per worker, then every later request pays only one cheap get_blob_properties() metadata call. metadata.dataset_from_cache reports which path a given request took, so the effect is visible in the response rather than merely claimed, and /api/health exposes the same state as dataset_cached.

Error handling: generic to the browser, detailed in the logs

Both data endpoints wrap their body in try/except Exception, call logging.exception(...), and return a fixed message such as {"error": "Failed to compute insights from the dataset."}. The exception text — which can contain the storage account name, container, blob path or SDK internals — never reaches the client. The detail is still available in Application Insights, which host.json enables.

8. Challenges & Solutions

A challenge is marked Solved only when something in the repository implements the fix. Where the fix is written but can only be confirmed against a live deployment it is marked Unverified, and where nothing implements it, Open.

#ChallengeSolutionOutcome / evidence
1 Duplicate CORS headers
Setting Access-Control-Allow-Origin in the function code and at the Function App host level makes Azure emit the header twice, which browsers reject outright.		 Keep exactly one layer. function_app.py emits no Access-Control-Allow-* headers at all (stated in its docstring) and deploy.sh step 7 removes any * wildcard before allowing only the Static Web App origin. Single-origin CORS is committed in code and script. Cannot be confirmed from a browser until the deployment runs. Unverified
2 Environment-specific URL in committed source
Hard-coding the Function URL in index.html would leak one team member's deployment into the repository and break for everyone else.		 index.html ships the placeholder __FUNCTION_API_URL__ and deletes window.NUTRITIONAL_API_URL if it was never substituted. deploy.sh copies frontend/ to a throwaway build/, rewrites the placeholder with sed -i "s#__FUNCTION_API_URL__#...#", and greps to confirm the substitution before deploying. Committed sources stay environment-agnostic and the build fails loudly rather than shipping a placeholder. Solved
3 Re-downloading the CSV on every request
Fetching and re-cleaning 7,806 rows per request wastes egress and adds latency to every call.		 Cache the cleaned DataFrame keyed by the blob ETag under a threading.Lock. Each request makes one cheap get_blob_properties() call; the CSV is re-downloaded only when the ETag changed, so a re-uploaded dataset is still picked up automatically. Repeat calls skip download and cleaning. metadata.dataset_from_cache and /api/health's dataset_cached make the behaviour observable rather than assumed. Solved
4 Large JSON response size
The full recipe payload for all 7,806 rows measures about 1.21 MB, which is slow to transfer and laggy to render as table rows.		 Server-side paging on /api/recipes: ?diet_type=&page=&limit=, default limit=50, hard cap 500, with count, total, page, limit and total_pages in the response. Bad input returns HTTP 400; an unknown diet returns 404. The frontend's Prev/Next/numbered buttons re-fetch from the server. A default page is roughly 1/156th of the full payload. Chart endpoints stay separate and return only ~5.8 KB of aggregates. Solved
5 Leaking internals through error responses
Returning str(e) to the browser would expose the storage account, container, blob path and SDK internals on any failure.		 Every handler catches broadly, calls logging.exception(...), and returns a fixed generic message such as "Failed to compute insights from the dataset." Detail goes to Application Insights, enabled in host.json. No storage detail can reach a client. Diagnostics are still available to the team in the logs. Solved
6 A dead API looking like a working dashboard
If the Function is unreachable, silently falling back to bundled data would show a marker a complete dashboard built from numbers that never came from the cloud.		 A failure on either data call switches the entire page to offline mode: a prominent full-width banner names the unreachable URL, the status badge turns amber, the source label reads "offline fallback", and the figures shown are the committed Project 1 batch results from Project1/docs/results/*.csv. Live and fallback data are never mixed in one view. Offline mode is unmistakable. This is the state the dashboard is in today, since nothing is deployed. Solved
7 Cold-start latency
A Consumption-plan Function can take several seconds to answer its first request, during which the dashboard would show empty chart frames.		 Per-chart loading spinners plus a dependency-free /api/health probe that answers without touching storage; the deploy.sh smoke test uses curl --max-time 180 so the first call absorbs the cold start instead of failing the script. Mitigations are in place, but no cold-start time has actually been measured because the app has never run in Azure. Unverified
8 Automated Azure deployment from CI
Pushing to main does not deploy anything to Azure.		 Not implemented. .github/workflows/deploy.yml runs the Project 1 build/test/Docker simulation, and the Project 2 CI job being added runs lint and unit tests only. Deploying from CI would require a publish profile or service principal stored as a GitHub secret, which this project deliberately avoids; deployment is therefore a manual ./deploy.sh run. No deployment job, no Azure credentials in CI. The trade-off (no secrets in the repository vs. no push-to-deploy) is a conscious one, but the automation is genuinely absent. Open
9 Static Web App region availability
az staticwebapp create fails in eastus, which is the region used for every other resource.		 Use a separate SWA_LOCATION=eastus2 for the Static Web App only, with the reason recorded in a comment next to the variable. The app is also created unlinked from GitHub so no repository token or OAuth grant is needed, and the frontend is uploaded afterwards with the swa CLI using a deployment token read from Azure. The script can create every resource without interactive GitHub authorisation. If the swa CLI is missing it prints the exact manual command instead of failing silently. Solved
